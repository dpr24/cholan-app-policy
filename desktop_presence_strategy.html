Architecture Guide

Desktop Presence Strategy

How to reliably and future-proof the detection of active Desktop App instances for online class authorization.

Why "App Close" Events Fail: Relying on the app to send a message when it closes is flawed. If a user force-kills the app via Task Manager/Activity Monitor, or if the OS crashes, or the computer loses power, the app never gets a chance to send the "I am closing" message. The server must actively verify the connection.
Recommended

WebSockets (Real-Time)

The industry standard for real-time presence. The app and server maintain an active, constant TCP connection.

  • Instant Kick-out: If the app is force-killed, the OS immediately severs the socket. The server knows instantly.
  • Low Overhead: Ping-pong packets are extremely lightweight compared to HTTP requests.
  • Ready to go: Your codebase already contains a WebSocketService reserved for future use.

How it Works

  • Connection: When the desktop app opens, it connects to your server via a WebSocket.
  • Ping-Pong: The server and the app constantly play ping-pong in the background (which is built into the WebSocket protocol).
  • Force Kill: If the app is force-killed: The Operating System instantly severs the TCP connection. Your server receives a disconnect event immediately and knows the app is gone.
  • Network Drop: If the internet drops: The server's ping times out, and it assumes the app is gone.
  • Future-proof: Your class web portal can instantly listen to the server. If the WebSocket disconnects, the web portal can instantly kick the student out of the video player.
📖 Real Life Example: A Phone Call You are on a phone call with the server. As long as the line is open, the server knows you are there. If your phone battery dies suddenly, the call drops instantly. The server immediately hears the "beep beep beep" and knows you are gone.

HTTP Polling (Heartbeat)

A simpler fallback method using standard REST APIs. The app periodically shouts "I am still here!" to the server.

  • Easy Implementation: Can be built using your existing ApiService in minutes.
  • Database Driven: Server updates a last_seen timestamp in the database on every pulse.
  • Slight Delay: Detection of an app crash is delayed by the interval time (e.g., up to 30 seconds).
Timer.periodic(Duration(seconds: 30), (timer) {
  _apiService.sendHeartbeat();
});

How it Works

  • New Endpoint: You create a new API endpoint on your server: POST /api/heartbeat
  • Timer: In your Flutter app, you set up a Timer that fires every 30 seconds to tell the server "I am still here".
  • Server Tracking: On the Server: You have a database table (e.g., active_sessions) with a last_seen timestamp. Every time the heartbeat hits, update last_seen = NOW().
  • Authorization: When the student tries to watch the class, the server checks: "Is this user's last_seen within the last 45 seconds?" If not, it means the app was closed or disconnected, and access is denied.
📖 Real Life Example: Security Guard Check-in You are a security guard who has to radio the base every 30 minutes to say "All good". If the base doesn't hear from you after 45 minutes, they assume you have left the building (or something happened) and lock down the area.

Decision Matrix

Choose WebSockets if

You need instantaneous detection when a student closes the app, so the web portal can instantly lock the video player. Best for strict security.

Choose HTTP Polling if

You want the fastest development time and are okay with a 30 to 60-second grace period before the system realizes the student closed the app.
